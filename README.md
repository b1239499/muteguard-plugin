# MuteGuard

被禁言（mute）的玩家，連 `/msg`、`/reply` 這類私訊指令也一併擋下。

## ⚠️ 重要更新：修掉了一個會洩漏訊息的 bug

**舊版本**判斷「玩家是不是被禁言」的方式，是送出一個模擬的、內容空白的
聊天事件，看看有沒有插件會取消它。這個做法後來被證實有嚴重副作用：
伺服器上另外運作的一支 Discord 轉發機器人，會不分青紅皂白地監聽任何
「聊天事件」並轉發出去——結果玩家每打一次 `/msg`，就會被那支機器人
誤判成一則「內容空白」的公開聊天，貼到 Discord 頻道裡，等於私訊被
間接洩漏（雖然只洩漏了空白內容，但已經足以讓別人知道「誰正在跟誰
密語」）。

**新版本**完全不再送出任何模擬事件。改成 MuteGuard 自己直接**監看
管理員執行 `/cmi mute`、`/cmi unmute`（或 `/mute`、`/unmute` 別名）**
這兩個指令本身（不管是玩家打的，還是從主控台下的），自己記一份「誰
現在被禁言」的名單，之後檢查私訊指令時只查自己這份記錄，不用去問
任何其他系統，也就不會再有東西可以被誤判成真實聊天。

代價：這份記錄不知道禁言的到期時間，如果 CMI 那邊的禁言時間到期
自動解除，MuteGuard 不會自動跟著解除（需要管理員手動 `/cmi unmute`，
或重啟伺服器讓記錄重置）。這個取捨是刻意的，換取「絕對不會再洩漏
訊息」的保證。

## 這是為了解決什麼問題

伺服器用 CMI 管理公開聊天禁言，但另外裝了一個獨立的 `Msg` 插件
（`spigotmc.org/resources/msg-plugin.80931/`）處理私訊。這兩套系統
互不相通：玩家被 CMI 用 `/cmi mute` 禁言後，公開聊天雖然被擋，但
`/msg`、`/reply` 私訊完全不受影響，等於禁言破功。

MuteGuard 在指令真正被任何插件處理**之前**就先攔截，判斷玩家目前
是否處於禁言狀態，是的話直接擋下指令，不讓 Msg 插件有機會執行。

## 設定 (`config.yml`)

```yaml
guarded-commands:
  - msg
  - m
  - w
  - tell
  - pm
  - reply
  - r
  - message

mute-message: '&c你目前被禁言中，無法傳送密語。'
```

- `guarded-commands`：要攔截的指令名稱清單（不含斜線），依照你
  `CustomAlias.yml` 裡實際設定的別名去增減。
- `mute-message`：被攔下時顯示給玩家的訊息，支援 `&` 顏色代碼。

## 權限

- `muteguard.bypass`（預設 op）— 就算被禁言，也能繼續使用私訊指令
  （方便管理員／客服帳號不受影響）。

## 編譯

跟 CatchMe 一樣，用 GitHub Actions 自動編譯：把整個資料夾（含
`.github` 資料夾）上傳到一個新的 GitHub 儲存庫，Actions 分頁會自動
跑起來，編譯完成後在 Artifacts 下載 `MuteGuard.jar`。
